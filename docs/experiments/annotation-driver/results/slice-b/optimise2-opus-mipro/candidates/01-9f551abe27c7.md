# Pack authoring guide, version 3

This is for mutation testing, the software testing technique that measures
how well a project's own test suite detects small deliberate changes to its
code. Each changed copy is run only against that project's tests in an
isolated checkout and is then discarded; nothing is deployed or executed
elsewhere. The tool that makes the changes is called the mutation engine.

The mutation engine reads one small JSON data pack per programming language.
The engine itself knows no language. It parses source files with the
tree-sitter grammar that ast-grep ships for the language, finds syntax nodes
the pack names, and rewrites them with the templates the pack gives. You
write the pack for one language.

The example packs show the format only. Do not copy their content: node kind
names, field names, operator spellings and templates differ between grammars
and languages. Work out every value from the target language's own
tree-sitter grammar.

The pack is checked by machine for four things: its shape, its size, whether
every node kind exists in the grammar, and whether known sample code
produces the expected result. An invented or misspelled kind fails the
whole pack. A missing or wrong kind changes the results on the sample code.

## Fields

Every node kind name must be the exact name of a visible node type in the
target grammar. Use the name as it appears in the parse tree, not a rule
name, alias or hidden/supertype rule (rule names starting with `_` never
appear as nodes). Field names must be exact field names from the grammar.

| Field | Meaning |
| --- | --- |
| `language` | The language name as ast-grep spells it, lower case |
| `comment_kinds` | Node kinds of comments, for every comment form the grammar has. Nothing inside them is ever touched |
| `string_kinds` | Node kinds of string literals, including raw, multi-line, interpolated or template strings and character literals if they are separate kinds. Nothing inside them is ever touched |
| `unwrap_kinds` | Node kinds of a parenthesis wrapper that the statement syntax requires around a condition. When a condition is such a wrapper, the engine works on the expression inside it. Leave empty when the language does not require parentheses around conditions |
| `test_attribute_markers` | Text fragments of attributes or annotations that mark test-only code inside a production file. Leave empty when the language keeps tests in separate files |
| `test_attribute_kinds` | Node kinds of the attribute or annotation items that can stand directly in front of a declaration and carry one of the markers. Required when `test_attribute_markers` is not empty. Leave the key out otherwise |
| `kinds.branch_condition.field_of` | Pairs `[node kind, field name]`. The named field of that kind holds a condition that decides control flow. Include each conditional statement, each loop with a condition, and each conditional expression, but only where the grammar really defines that field |
| `kinds.branch_condition.returned` | `{"of", "kinds", "tokens"}`. `of` lists the node kinds of a return. `kinds` lists the kinds of binary/logical, comparison and unary/negation expressions. `tokens` lists the logical and comparison operator tokens as the language spells them. A returned expression of one of these kinds with one of these operators counts as a condition |
| `kinds.failure_state.nodes` | Node kinds that signal failure to the caller: throwing or raising, returning, and error propagation where the language has a dedicated syntax for it |
| `kinds.failure_state.nodes_with_prefix` | Optional. Maps a node kind to text prefixes, for failure signals that are ordinary calls or macros and can only be told apart by how they begin |
| `kinds.error_order.nodes` | The node kind of a conditional statement that can directly follow another of the same kind. Always add `"requires_next_sibling": true` |
| `kinds.state_write.nodes` | Node kinds of assignment, compound assignment, and increment/decrement updates |
| `kinds.state_write.call_statements` | Node kinds of a call, and of an awaited call where the language has one, that can stand alone as a statement |
| `kinds.pure_shell_boundary.nodes` | Node kinds of function, method and constructor definitions. Do not include lambdas or closures |
| `noop_statement` | Text of a statement that does nothing and is valid wherever a statement may stand |
| `statement_wrappers` | Node kinds that wrap an expression to make it a statement. Leave empty if the grammar has none |
| `statement_terminator` | The token that ends a simple statement, if the language requires one. Leave the key out otherwise |
| `gaps` | Optional. A list of `{"reason", "nodes_with_prefix"}` entries for general language features whose effects tests cannot observe, such as reflection or dynamic evaluation. Never list things specific to a library or project |

## Operators

`operators` tells the engine how to rewrite a site. Templates may use
`{text}` (the node's text), `{noop}` (the `noop_statement`) and `{child0}`
(the text of the node's first named child).

| Entry | Meaning |
| --- | --- |
| `operators.branch_condition.template` | Replaces a condition with its logical negation, using the language's own negation operator or keyword. Always wrap `{text}` in parentheses so the result parses for any condition |
| `operators.branch_condition.token_swaps` | Pairs of operator tokens that can replace each other without changing the expression's type: equal and not equal, strict and non-strict comparison, logical and and or. Spell them exactly as the language does. Include a pair only if both tokens exist in the language |
| `operators.branch_condition.negation_swaps` | The pairs from `token_swaps` whose swap gives exactly the logical negation: equal and not equal, in every spelling the language has. Never list strict/non-strict comparison pairs or and/or pairs |
| `operators.branch_condition.exclude_kinds` | Optional. Node kinds that can stand in a condition position but cannot be negated by the template, for example a pattern-binding condition, a declaration used as a condition, or an empty condition |
| `operators.failure_state.by_kind` | Maps a node kind to a template that removes the failure. Use `{noop}` only for kinds that are always complete statements and can simply be dropped. Leave out returns and any kind that can appear as an expression |
| `operators.failure_state.returned_literal_swaps` | Pairs of literals that can replace each other as a returned value: the two boolean literals in the language's spelling, and `0` and `1` |
| `operators.state_write` | Always `{"statement": "{noop}"}` |
| `operators.error_order` | Always `{"swap_next": true}` |

## Rules

- Precision matters more than coverage. A wrong kind produces changes that
  do not parse or do not compile. If you are unsure whether a kind or field
  exists in the grammar, leave it out.
- Check every kind against the parse tree that the grammar produces for
  simple code: a conditional, a loop, a return of a comparison, an
  assignment, a call statement, a throw or raise, and a function
  definition.
- Do not include anything specific to a particular project, library or
  file.
- Leave out optional keys you do not need, but always include every
  required key.
- Keep the pack small: at most 40 lines and 2,500 characters, formatted
  like the examples.

## Output

Return only the JSON object of the pack. Do not add text before or after
it, and do not put it in a code fence.
