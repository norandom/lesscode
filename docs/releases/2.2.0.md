# Lesscode 2.2.0

Prepared 2026-11-24. The owner chose the number on that day. Nothing is tagged or published yet,
and the version in `native/Cargo.toml` is still 2.1.0. The tag `v2.2.0` is pushed by the owner; the
release workflow then builds, signs and publishes the archives ([release signing](../release-signing.md)).

Proposed tag message:

> Lesscode 2.2.0: a page that shows a run while it goes on and is its report at the end (`--open`, `--page`); a list of several reports (`step reports`); the copies of a run take turns by free memory; the brownfield test stage (`step protect begin`, `step protect result`)

## What is new

- **A page that shows a run.** `step plan` and `step check` take `--open` and `--page`. With `--open`
  your default browser opens on a page that follows the run while it goes on; it is served from
  your machine only and ends with the run. With `--page` the report of the run is written as one
  HTML file at the end, and nothing is served. The page comes inside the binary and loads nothing
  from the network. Guide: [refactoring in checked steps](../steps.md#watch-the-run-in-a-browser---page-and---open).
- The page says first that no file of your project is changed and where the copies are. Under that
  the steps of the run stand in one row, with the one that is going on marked. It explains a
  planted fault with one of the run, lists the functions in which no fault was noticed, and says
  what to do with them.
- For `step check` the page ends as a report: the outcome in one box, the same for accepted,
  refused and not judged; a tile and a row per lens with the direction expected; the functions and
  calls before and after. `--measures <file>` adds numbers of the state and local-complexity lenses
  that were measured elsewhere.
- `step reports <report>... --out <directory>` writes one page that lists several reports, with a
  copy of each. `--without-names-of <project>` puts numbers where that project's files, functions
  and types are named.
- `--page-source` shows the line of code of the example fault. Without it the page holds names
  and no source text.
- A language pack can name the code that is not built on the current system. Faults planted there
  are counted apart and the page says that they tell nothing.
- A language pack can name fields no caller sees. A string argument of a call that is the value of
  such a field is not emptied. The Rust pack names `label`, the debug name of wgpu and egui
  descriptors. On `yuv.rs` of a renderer, 11 of the 12 faults the tests missed were such labels;
  a new plan drops 7 of them. The other 4 are labels passed to a helper that sets the field in its
  own body, which the rule does not see.
- A language pack can name the kinds of argument that are bound by name. The first two arguments
  of a call are not swapped when the first is one of them. The Python pack names keyword
  arguments, which mean the same in either order. On the Python file of the stage's third walk,
  this drops the one fault left there, which the owner had to write off.
- **The brownfield test stage: protect what you will change.** Between a plan and a reduction, the
  stage adds tests and changes no code. By default it protects every function of the plan in which
  the tests missed a planted fault; `--function` narrows it to the functions you are going to make
  smaller, and the others with missed faults are reported without holding the stage back.
  `step protect begin` writes the stage's declaration and `stage.json` from the plan, and says
  before anything runs which faults will be run again, about how long the base run and the check
  each take with room for a busy machine, and what the copies take on disk. The time figures count
  every run of the tests a run makes besides the faults. In three walks of the stage no run took
  more than 1.05 times its figure. `step protect result` says by exit code
  whether each chosen function is protected enough (0), a fault still waits (1), or nothing was
  judged (2), and leaves `protection.json`. It reads the verdict and the approved write-offs as
  they are committed on the branch, so a pipeline and a person get the same answer for the same
  commit. Both commands run nothing themselves, open no page and ask nothing. An agent walks the
  stage with the new skill `protect-before-reduce`. Guide:
  [protect what you will change](../steps.md#protect-what-you-will-change-step-protect).

## Changed

- `step check` can now end with 2, not judged, where it ended with 1, refused: when no test ran at
  all in any copy on the unchanged code. A pipeline that reads the exit code sees the difference.
  The owner took this as a correction and the release as a minor one.

- A run without `--page` and `--open` writes what it wrote before and prints what it printed before.
- The copies of a run take turns by the memory that is free. The first build of a copy and the first
  build with a planted fault run alone once and are measured; after that a run starts beside others
  only when the memory holds them. Three copies of a Rust project that needs about 8 GiB for a full
  build ran to the end on a machine with 13 GiB free, where they had run out of memory before. With
  little memory the copies mostly run one after another, which is slower and gets through.
- A copy whose first run fails says whether its commands ended before any test ran or a test did not
  pass (this needs `runner_evidence_patterns` in the configuration), keeps the whole output in
  `first-run-w<copy>-<attempt>.log` under the work directory, and tries once more when no other copy
  is in its first run. A run in which no test ever ran is "not judged" for `step check`, where it
  was "the project's tests do not pass" before.
- The receipt of a run names a copy's first attempt under `retried` where a second one was made.
- The verdict of `step check` names, per function, the faults the tests did not notice on the base
  (`unnoticed_before`), as it named those after the step. `step protect result` uses it: a fault
  that a flaky test made the plan count as noticed, and that the base run did not notice, is
  taken into the stage and can be tested or written off.

## Known limits

- How much memory a run takes is read from the whole system while the run goes on alone. Another
  program that takes memory at that moment makes the number too large, and the copies then wait
  more than they need to. The number of copies is not lowered; they wait for their turn.
- On macOS the system is not asked how much memory is free, and nothing is held back.
- The page was checked in Chromium, and earlier in Edge. Firefox, Safari and a screen reader were not tried.
- `--open` on Linux starts `xdg-open`, on macOS `open`. macOS was not run.
- The brownfield test stage was walked once by hand and three times with its two commands: twice on
  a renderer written in Rust and once on a Python project, whose tests ran in a Linux container.
  The disk figure of `step protect begin` leaves out what a project builds outside the copy.
- The Python pack still swaps a positional argument with a keyword argument that follows it. The
  grammar accepts the result, but Python refuses to compile it, so the tests count the fault as
  noticed.
- Plans made before this release still list the label faults of Rust code; make the plan again to
  drop them.
- `step protect result` cannot know that the owner of the code wrote an approval. It prints every
  approver and date so that a false one is seen.
