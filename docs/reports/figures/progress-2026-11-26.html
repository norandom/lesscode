Lesscode Progress Report

Lesscode research · written 26 November 2026, Europe/Berlin · covers 18 to 26 November

Tests first, then the rework: what the last eight days showed

Lesscode is a research tool for making code smaller and less entangled without changing what it does. This report says what changed since the reports of 9 and 11 November, adds the measures that are new, and shows six reworks in three projects before and after.

Numbers like R164 point to entries in the research log (docs/research in the repository). They are pointers, not names.

The answer first

The report of 9 November claimed that the reworked code was checked by planted faults and by a solver. An audit on 17 November found that neither check had run on the reworked code. Since then:

  1. Planted faults run on real code and decide. The released tool planted 268 faults in a seven-file subsystem of a real application. A rework is now refused when any function it touches ends with more faults that the tests do not notice.
  2. State is counted. For a type, the tool's research programs count the places that hold state, the ways the type can be written, the ways the code reaches, and the ways the tests see.
  3. Tests come before the rework. A new stage has an agent write tests for the faults the existing tests miss. What cannot be tested is written off by the owner, and only a signed commit of the owner counts.

With these in place, two reworks of a real application were judged by the released tool and accepted: one type went from 16 ways to be written to 6, and one decision that was held in two places that could disagree is now one value. Neither made the code smaller in any way that matters. The gain is in the state.

Fault injection: from a claim to a gate

A planted fault is a small deliberate bug: a negated condition, a dropped statement, two arguments swapped. The tool plants one at a time in a copy of the code and runs the project's tests. If a test fails, the fault was noticed.

  1. 10–11 NovA Python prototype plants 66 faults in one Rust file of another project; the tests notice 45 (R64).
  2. 17 NovThe audit finds that the "100% noticed" of the 9 November report was never run on the reworked code (R134).
  3. 18 NovFour planted faults per subsystem are detected on both versions of the two Python subsystems (R138).
  4. 23 NovThe released binary plants 268 faults over the seven files of a renderer in 1 hour 43 minutes (R164). The chart below is that run.
  5. 23 NovA rework is judged by faults per function for the first time: refused once for size, then accepted (R173).
  6. 24 NovThe stage that protects code before it is reduced gets two commands and a skill an agent follows (R184 to R187).
  7. 24–25 NovThe stage runs on three real files in two languages (R188 to R190).
  8. 25–26 NovA write-off counts only as the owner's signed commit, checked against the project's signer list and GitHub (R192 to R197).
  9. 26 NovA rework over six files is judged and accepted. On the way the tool could not judge a step that deletes a file; that defect is fixed and has a test (R198).

What is not shown

About the reworks

  • Three planted faults in the display-path rework sit in glue code that no test of the project can reach. The owner chose to rework with them reported, not protected.
  • To stay within a growth of zero tokens, a two-case enumeration became a tuple. It is smaller and names its cases less clearly. The size limit caused that.
  • Nobody has been asked whether the reworked types are easier to read. The state counts say a meaningless shape is gone, not that a reader is faster.
  • The second Python subsystem has no solver check.

About the tool

  • The state counts come from research programs, not from the released tool. The released check shows them only when they are handed in.
  • The finder of scattered state does not see a plain field assigned in many places, which was the largest state machine of drift-rdp.
  • Faults in code built only on Linux were not run on Windows.
  • One copy of drift-rdp's tests fails its first run on a fresh copy and passes the second. That was not investigated.

About approvals

  • No signed approval has yet been counted against the real GitHub. The owner stopped that task.
  • The owner's approval key has no passphrase, by the owner's decision. Anything that can read the key file can sign.
  • Version 2.2.0 is not published. Its publish job waits for the owner.

How this is meant to be taken up

The same three questions the method asks of any knowledge that should become practice: where does it land, what is the message, and through whom does it spread.

Where it lands

A developer who is asked to let a tool near working code expects damage. So the first sentence is always that no file of the project is changed: faults are planted in copies. The roles are fixed. The tool measures and judges, an agent following a skill writes, and the person decides, with a signed commit.

The message

One action: before reducing a file, run the plan, let the stage write the missing tests, and review the write-offs once. Four commands carry it: step plan, step protect begin, step protect result, step check. Each answers by exit code, so it runs in a pipeline.

Through whom

So far only the owner's own projects: drift-rdp, scitools-hook, and lesscode itself. The next step that would say something is a project with its own tests and another maintainer. This part is a proposal, not a result.

We are wrong if

  • a step the check accepted later turns out to have changed behaviour that one of the project's tests should have caught;
  • on a project the tool was not developed against, the stage needs a step done by hand;
  • readers of a reworked type do not find the answer to "what can this value be" faster than before.
