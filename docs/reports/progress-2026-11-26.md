## The answer first

The report of 9 November claimed that the reworked code was checked by planted faults and by a solver.
An audit on 17 November found that neither check had run on the reworked code (R134). Since then:

1. Planted faults run on real code and decide. The released tool planted 268 faults in a seven-file
   subsystem of a real application (R164). A rework is refused when any function it touches ends with
   more faults that the tests do not notice.
2. State is counted. For a type, research programs count the places that hold state, the ways the type
   can be written, the ways the code reaches, and the ways the tests see (R165 to R170).
3. Tests come before the rework. A stage has an agent write tests for the faults the existing tests
   miss. What cannot be tested is written off by the owner, and only a signed commit of the owner counts
   (R184 to R197).

With these in place, two reworks of a real application were judged by the released tool and accepted.
One type went from 16 ways to be written to 6 (R173). One decision that was held in two places that
could disagree is now one value (R198). Neither made the code smaller in any way that matters. The gain
is in the state.

## What is not shown

About the reworks:

- Three planted faults in the display-path rework sit in glue code that no test of the project can
  reach. The owner chose to rework with them reported, not protected.
- To stay within a growth of zero tokens, a two-case enumeration became a tuple. It is smaller and names
  its cases less clearly. The size limit caused that.
- Nobody has been asked whether the reworked types are easier to read.
- The second Python subsystem has no solver check.

About the tool:

- The state counts come from research programs, not from the released tool. The released check shows
  them only when they are handed in.
- The finder of scattered state does not see a plain field assigned in many places, which was the
  largest state machine of drift-rdp (R159).
- Faults in code built only on Linux were not run on Windows.
- One copy of drift-rdp's tests fails its first run on a fresh copy and passes the second. That was not
  investigated.

About approvals:

- No signed approval has yet been counted against the real GitHub. The owner stopped that task.
- The owner's approval key has no passphrase, by the owner's decision (R197).
- Version 2.2.0 is not published. Its publish job waits for the owner.

## How this is meant to be taken up

- Where it lands: a developer who is asked to let a tool near working code expects damage. The first
  sentence is that no file of the project is changed: faults are planted in copies. The tool measures and
  judges, an agent following a skill writes, and the person decides, with a signed commit.
- The message: before reducing a file, run the plan, let the stage write the missing tests, and review
  the write-offs once. Four commands carry it: `step plan`, `step protect begin`, `step protect result`,
  `step check`. Each answers by exit code.
- Through whom: so far only the owner's own projects, drift-rdp, scitools-hook and lesscode itself. The
  next step that would say something is a project with its own tests and another maintainer. This part
  is a proposal, not a result.

We are wrong if:

- a step the check accepted later turns out to have changed behaviour that one of the project's tests
  should have caught;
- on a project the tool was not developed against, the stage needs a step done by hand;
- readers of a reworked type do not find the answer to "what can this value be" faster than before.
